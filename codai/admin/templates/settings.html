Thermal Protection
Before serving a request against a loaded model, wait until temperatures are safe so a long sequence of heavy generations can't overheat the machine and trip its power-off protection. The wait is non-blocking (other requests keep being accepted) and takes effect immediately on save. Temperatures in °C.

DeepSeek V4 (ds4)

Run DeepSeek V4 through antirez's native ds4 / DwarfStar engine as a managed subprocess. When enabled, requests for a matching model name are proxied to ds4-server. First use clones + builds ds4 and downloads several GB of weights — this is slow and needs lots of RAM (96 GB+).

Fetches an official GGUF from antirez/deepseek-v4-gguf straight into the gguf cache, where it appears in the model list to configure. Large (tens to ~150 GB) — runs in the background.
When enabled, ds4 automatically serves any deepseek4-architecture GGUF you have (detected by reading the file); mainline DeepSeek GGUFs stay on llama.cpp. This alias also routes (for ds4's own downloaded variant).
Only used when auto-download is enabled below.
Force ds4-server to load this exact GGUF (skips the variant download). Leave blank to auto-serve the requested deepseek4 model.
Point at a ds4-server running on another host or a rented pod. Nothing is built, downloaded or launched locally — coderai proxies to it and checks its health first.
Passed verbatim to ds4-server. --kv-disk-dir is auto-set to coderai's offload dir unless you override it here. With SSD streaming on CUDA, sizing the routed expert cache helps, e.g. --ssd-streaming-cache-experts 12GB. Note: extremely low quants (Q2_K) can fail ds4's CUDA prefill — prefer Q4_K+.
Exports DS4_CUDA_STREAMING_EXPERT_CACHE_RESERVE_GB — VRAM ds4 keeps free for non-cache use under SSD streaming. ds4 defaults to half the card, which over-reserves for small-weight MoE models and caps the expert cache far below your --ssd-streaming-cache-experts request. Set just above the model's resident weights (+~2 GiB headroom) to hand the rest to the cache; 0 leaves ds4's default. There is no CLI flag for this — it's env-only.
Whitespace-separated KEY=VALUE pairs added to ds4-server's environment — for the many CUDA tunables it exposes only via env. Notably DS4_CUDA_WEIGHT_ARENA_CHUNK_MB (default 1792): lower it (e.g. 512) so the weight arena allocates in smaller chunks that fit a heap fragmented by the streaming expert cache, fixing model arena alloc failed … out of memory.
These are global defaults; override them per-model on the Models page (a big-quant streamer and a small one that fits VRAM want different settings). Order of impact:
• Put the GGUF on a fast NVMe/SSD, not a spinning disk — for a streamed MoE this is the single biggest win (≈10× prefill). A symlink from the old path works.
• Cap the expert cache with --ssd-streaming-cache-experts N (a COUNT, e.g. 400 — not NGB). Bigger = better decode hit-rate, but too big fragments VRAM and the weight arena OOMs; find the ceiling for your card.
• Reserve ≈ resident weights + ~2 GiB (field above). ds4 defaults to half the card, which starves the cache.
• Add DS4_CUDA_WEIGHT_ARENA_CHUNK_MB=512 (env) to stop the weight-arena OOM under heavy caching.
• Avoid DS4_CUDA_WEIGHT_CACHE — it disables ds4's zero-copy path and was slower in testing.
• Decode of a model far larger than VRAM is streaming-bound (~0.5 tok/s here); a smaller quant that mostly fits VRAM+RAM is the only real decode fix. But i-quants (IQ2/IQ3) and Q2_K fail ds4's CUDA prefill (gpu layer 0 ffn batch encode failed → empty reply) — they load but can't generate. Use K-quants Q4_K and up. Context window is set per-model via n_ctx.
ds4 writes prompt KV checkpoints to its --kv-disk-dir (<offload>/ds4-kv) to reuse prefixes across requests; abandoned sessions accumulate large files that never self-prune. When on, a janitor deletes a checkpoint only when BOTH: its newest file is older than the age below, AND no running ds4-server currently has it open (fd or mmap). Files ds4 is actively using are always kept, regardless of age.
GLM-5.2 (colibri)

Run GLM-5.2 through JustVugg's pure-C colibri MoE engine. Unlike ds4, colibri ships no server — coderai drives the C engine binary directly over its stdin/stdout mux protocol (no colibri Python at runtime). First use clones + builds the engine (CUDA when available). The GLM-5.2 int4 container (~372 GB directory) is not downloaded automatically — point the model path at it (see the int4 g64 + int8-MTP container).

Fetches the full HF repo (a directory of int4 shards, ~372 GB) like any other model and registers it as a colibri-backed model pointing at the snapshot dir. Keep the HF cache on fast storage (NVMe/ext4). Resumable.
When enabled, this id (and names containing glm-5.2 / colibri, or any model whose config backend is colibri) routes to the colibri engine.
The GLM-5.2 int4 container directory (engine env SNAP). Keep it on fast local storage (NVMe/ext4), never on a network mount. Leave blank to serve the requested model's own configured directory.
1–16 concurrent cached conversations (continuous batching).
Engine worker cap (positional arg).
Exports CUDA_EXPERT_GB — size of the resident expert tier colibri pins on the GPU. Blank leaves colibri's auto sizing.
Point at a colibri engine hosted by tools/mux_service.py elsewhere. Nothing is built, downloaded or launched locally — coderai proxies to it and checks its health first.
Whitespace-separated KEY=VALUE pairs added to the engine's environment — colibri exposes its tuning only via env (COLI_MODEL_MIRROR, COLI_DISK_WEIGHTS, COLI_NUMA, COLI_CUDA_PIPE, DIRECT, PIPE, PILOT, DRAFT, …). Context window is set per-model via n_ctx.

colibri v1.5.0 also serves DeepSeek-V4 and Kimi-K3 (CPU engines) from the same install — add a model whose backend is colibri pointing at that family's container; the engine auto-detects the family from the container's config.json.

Kimi-K3 (kimi-k3-in-c)

Run Kimi-K3 through FareedKhan-dev's portable-C kimi-k3-in-c engine. coderai patches in a resident serve loop and drives it over the same mux protocol as colibri. CPU-only (AVX2+FMA) and needs ~1.7 TB fast local storage (the ~1.56 TB checkpoint + a ~109 GB packed trunk from the repo's scripts/pack-trunk.sh). Nothing is downloaded automatically.

When enabled, this id (and names containing kimi-k3, or any model whose config backend is k3) routes to the k3 engine. If colibri is also enabled, a bare Kimi name is ambiguous — set the model's backend to choose.
The Kimi-K3 checkpoint directory (config.json + tokenizer + safetensors shards).
Point at a k3 engine hosted by tools/mux_service.py elsewhere. Nothing is built, downloaded or launched locally — coderai proxies to it and checks its health first.
The packed dense trunk (scripts/pack-trunk.sh). Blank = fully resident (needs ~114 GB RAM).
Whitespace-separated KEY=VALUE pairs (K3_EXPERT_GB, K3_BITS, K3_DIRECT, K3_PIPE, …).
ktransformers (SGLang)

Run many large MoE families (DeepSeek, Kimi, Qwen, GLM, MiniMax) through ktransformers' CPU+GPU heterogeneous engine, served over SGLang's OpenAI API. coderai launches python -m sglang.launch_server as a managed subprocess and proxies to it. Requires SGLang + kt-kernel installed out of band (best on AMX/AVX-512 CPUs). Selected per model via an explicit backend: kt pin or the model id below — never by a broad name marker.

vLLM (high-concurrency)

Serve an LLM (or VLM) through vLLM's OpenAI server with continuous batching — far higher aggregate throughput than serialized single-instance backends. coderai launches vllm.entrypoints.openai.api_server as a managed subprocess and proxies to it. vLLM pins its own torch/CUDA, so it runs in an isolated venv (CUDA-only). Selected per model via a backend: vllm pin or the model id below. Also serves Surya2 for OCR.

Leave blank and tag models in the Models list with backend: vllm (like nvidia/radeon) — vLLM serves each by its own path. Set an id/path only to serve a single model that has no list entry.
vLLM is CUDA/NVIDIA-only. Pin it to a specific card (e.g. 0) to dedicate a GPU, or list several (0,1) with a matching TP size.
Point at a vLLM OpenAI server elsewhere — RunPod publishes a ready-made vLLM image. Nothing is built, downloaded or launched locally — coderai proxies to it and checks its health first.
Several machines over Ray (defaults; a model's own vLLM block overrides)
Tensor parallel splits every layer across the GPUs of one machine (fast links); pipeline parallel gives each machine a slice of layers — use that across a network. With nodes listed coderai starts a Ray head here, runs each node's command ({ray_address}, {head}, {port} filled in), waits until Ray sees tensor×pipeline GPUs, then launches vLLM on Ray. The coderai-vllm image joins as a worker when started with CODERAI_RAY_ADDRESS.
Cluster

Other coderai installs on your network become engines of this one: this front polls each node's state, assigns models to it, pins a model to it by name on the Models page (Engine / card), and routes requests there by capability and load — the node's own front picks the card. A node needs only an API token created on its Tokens page. This section also lists the llama.cpp rpc-server processes this machine runs to lend its cards to a GGUF loaded on another node (per model: Cards on other machines). RunPod (remote GPUs)

Burst inference to rented GPUs on RunPod — as Pods (coderai provisions, load-balances and autoscales them) or Serverless endpoints (RunPod autoscales). Uses no local VRAM: coderai proxies OpenAI requests to the remote GPU. Set the account key here, then tag a model in the Models list with backend: runpod and its per-model pod/serverless block. These are the account-wide settings shared by every RunPod model.

Your RunPod API key. Stored server-side, never logged. Leave blank to keep the current key.
Instantaneous rate: total $/hr across all running pods.
Cumulative spend across all RunPod models over the period below.
Pods attach it at launch, so downloaded weights, uploaded models and LoRA adapters survive the pod — the second pod does not re-download. Secure Cloud only, and pods are pinned to the volume's data center.
From RunPod → Settings → Container Registry Credentials. Needed for a private pod image; public ones (vLLM, llama.cpp) need none.
Tags pods as yours (coderai-<id>-…) so the stale-pod reaper only ever stops your own pods. Use distinct ids for separate coderai deployments on one account.
Advanced API endpoints
Remote capabilities

Images, video, embeddings, TTS, STT and the rest load their model in this process, so there is no per-model way to move them. Point a capability somewhere else and matching /v1 requests are forwarded there instead — to another coderai, or to a RunPod pod coderai provisions, scales and reaps for you. Per-model service_url still wins over anything set here. Chat and completions are not listed: those are per-model, on the model's own page.

A managed pod uses its own generated token instead; this is for URLs you run yourself.
Larger uploads are served locally rather than buffered in RAM.

A pod row left blank uses the published ghcr.io/nextime/coderai-<capability> image — a trimmed coderai carrying only that capability. Override it to run your own build (packaging/runpod/publish_capability_images.sh). Give several capabilities the same pool name and they share one pod and one budget.

OCR (document → text)

Dedicated OCR engines (detection + recognition), not a vision LLM — faithful text with bounding boxes and layout, batched on GPU. Serve PaddleOCR, docTR or Surya, selectable per request. Endpoints: POST /v1/ocr, POST /v1/ocr/batch. Heavy deps install out of band (pip install -r requirements-ocr.txt or ./build.sh … --ocr); a missing engine returns HTTP 503.
